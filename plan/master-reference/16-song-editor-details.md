## 16. Song Editor Details

`SongEditor.jsx` is a full-screen modal (via `createPortal`). Key internals:

**Two-row formatting toolbar (`FormattingToolbar`)** — row 1 (always visible): font family, font size, colour swatch, bold, italic, underline, *text* align L/C/R/justify, *text* vertical align T/C/B (within the box), letter spacing, uppercase, reset. Row 2 (template-dependent):
- Fullscreen channels: text box **Fill** (box = content window) + **object-align** buttons (`align_horizontal_*` / `align_vertical_*`, snap the box within the content window via `objAlign('h'|'v', …)`) + manual X/Y/W/H inputs
- Lower-third channels: bar toggle (On/Off), colour swatch, opacity slider, solid/gradient toggle
- `simple` prop (scripture reference target) hides v-align/text-box/bar and adds a Pos Bottom/Free + X/Y control for the reference `pos`

`previewTemplate` prop determines which row 2 is shown. `FormattingToolbar`, `SlidePreview`, `LowerThirdPreview`, `copyrightCss`, `copyrightFontCss`, `renderWithRuns`, `DEFAULT_STYLE`, `styleIsDefault` are **exported** from `SongEditor.jsx` and reused by `ScriptureEditor.jsx` and `PreviewLivePanel.jsx`.

**Run-level styling** — selected text gets bold/italic/underline/colour/font overrides stored as `runs: [{start,end,...}]` in `style_json`. `renderWithRuns(text, runs)` converts to `<span style="...">` HTML.

**Live preview pane** — always-visible `SlidePreview` (fullscreen) or `LowerThirdPreview` (lower-third), rendered at 1920×1080 then CSS-scaled (height-bound 16:9 box so it never overflows the footer). Background picker wired to `songs:setBackground`.

**PowerPoint-style positioning (editor previews)** — a fixed `CONTENT_BOX = {x:5,y:5,w:90,h:90}` "content window" (safe-area guide) is drawn over the background. `style.textBox{x,y,w,h}` is the text box: **drag** the body to move, **8 resize handles** (`TB_HANDLES`, counter-scaled to constant visual size; `resizeBox()` keeps the opposite edge fixed) to resize, anywhere on screen. *Text align* aligns text within the box; *object align* snaps the box within the content window. The reference is draggable too (`onRefPosChange`; converts bottom-anchor → `pos{x,y}` via bounding-rect measurement, no jump). `SlidePreview` props: `onTextBoxChange`, `onRefPosChange`. Output already honours `textBox.h` + `verticalAlign`, so positioning is editor-only — no template changes. The `GraphicsEditor` box previews (`BugPreview`, `CountdownPreview`) draw the same content-window guide (`ScaledFrame contentGuide`) and their object-align snaps to the same `CONTENT_BOX`; boxes still drag anywhere on the frame.

**`ltBar`** — `null` by default (transparent lower-third bar). When set: `{ color, opacity, solid }`. `buildBarBg(ltBar)` computes a `linear-gradient` (default) or `rgba()` solid. Same function duplicated in `SongEditor.jsx`, `PreviewLivePanel.jsx`, and `lowerthird.js`.

**Continuous lyrics document** — the lyrics pane is ONE `contentEditable` (EasyWorship-style), not a per-section list. Each section is a non-editable `data-head` line (a coloured type chip carrying `_key` + type) followed by its text; inline `⁂` slide breaks (⌘Enter) render as `data-break` lines. Typing `Chorus` (or any recognised header) + Enter on its own line starts a new section; pasting a whole song splits it into sections at the caret.
- **DOM → state** on every input (`extractSongSections`, coalesced undo). **State → DOM** (`renderSongHtml`) only on load, structural edits and undo/redo, driven by `domSyncTick` in a layout effect that places the caret synchronously, so the caret and the highlight frame stay put through undo/redo.
- **Slide-break rendering:** manual `⁂` breaks and max-lines auto splits look identical (gutter scissors + faint dashed rule; only the tooltip differs). Auto splits are an overlay (`computeAutoMarks`), never inserted into the DOM. Header slide numbers count both kinds.
- **Clipboard:** copy writes a lossless `application/x-cue-song` payload (types, breaks, runs) plus labelled plain text; ⌘⇧C copies lyrics only. Paste prefers the Cue payload (copying between songs keeps sections + formatting), then the shared lyrics parser. Read-only views (Library preview, rundown preview) use `utils/lyricsClipboard.js useLyricsCopy` for the same ⌘C / ⌘⇧C behaviour.
- **Sections created in the editor** join an existing arrangement (`restructure(..., added)`) so they reach the screen. ⌘S saves.
- **Formatting toolbar** controls are 13px with icon alignment buttons; line height, shadow, outline and lists sit directly on the bar. `ScriptureEditor.jsx` follows the same layout (verse/reference cards, background, and a "Preview with" box that renders any typed reference).

**Lyrics parser (`src/shared/lyrics-parse.js`)** — the ONE lyrics → sections parser, used by the editor paste, file import (plain text / ChordPro / EasyWorship / GHS), the web scraper, and set-list "create from lyrics". `parseLyrics(raw)` returns `{sections, arrangement}`:
- Recognises decorated (`*Verse 1*`, `[Chorus]`, `CHORUS:`), abbreviated (`V1`, `Ch`, `PC`, `Br`) and misspelt headers; ambiguous words (`bridge`, `end`, `build`) only count as headers when the rest of the line is clearly an annotation, and single letters (`C`, `B`) need a number/colon/brackets (they double as chord names).
- Strips singer annotations on headers (`Verse 1 — Mary`, `Mary - Verse 1`, `(Mary) Verse 2`, `Solo - Tammi`) and directive lines (`All`, `Men:`, `Leader:`, `Tammi: …`), conservatively so ordinary lyric lines survive.
- Drops chord-only lines, inline chords, CCLI/SongSelect footers and `(x2)` markers; "Repeat chorus" placeholders and repeats fold into the `arrangement` (play order) instead of duplicated text. Callers that create songs must persist that arrangement.
- **Delete-only invariant:** every transform only deletes characters or drops lines, so each section stays a subsequence of the source (EasyWorship run recovery in `deriveStyleJson` depends on it).
- Tests: `lyrics-parse.test.mjs` (in `npm test`); regression-check changes against `resources/ghs/ghs-hymnal.json`.
- **Clean up singer notes** (Library tool, `SingerNotesCleanupModal.jsx`): `songs.scanSingerNotes()` previews which existing songs still carry annotations from before the parser handled them; `applySingerNotes(ids)` cleans the chosen ones with runs re-aligned.

**Section ordering** — section order is the document order; play order is the arrangement (below). Section labels number via `utils/sectionLabels` (Verse 1 / Verse 2), derived from the natural section list so an arrangement-repeated chorus stays "Chorus".

### Song import (`src/main/import/songs-import.js` + `SongImportModal.jsx`)
File import is a two-phase preview/commit flow: `songs.importParse(filePaths)` parses (no DB write) → `SongImportModal` lets the operator deselect rows and edit titles → `songs.importCommit(rows)` bulk-inserts. The Songs-tab **Import** dropdown offers "Import from File…" and "Import GHS Hymnal".

`parseSongFiles` auto-detects per file (never throws — a bad file is a `{ok:false, error}` row):
- **OpenLyrics XML** — regex parse (no XML dep, matching `bible-import.js`); title/authors/copyright + CCLI from `<properties>`; verse `name` codes (`v`/`c`/`b`/`p`/`e`…) → section types; `<br/>`→newline, chords/comments stripped.
- **ChordPro** — `{title|artist|copyright|ccli}` directives extracted; `{soc}`/`{sov}` markers → section headers; inline `[C]`/`[G7]`/`[D/F#]` chord tokens stripped (real `[Chorus]` headers survive).
- **Plain text** — filename → title; body run through `parseSections` (the shared header/blank-block splitter, same rules as the editor's Paste Song parser).
- **EasyWorship** — picked `Songs.db` (or `SongWords.db`, sibling auto-resolved); both are SQLite read via `better-sqlite3`. Lyrics live in `SongWords.word.words` as **RTF**, joined by `word.song_id = song.rowid`. `rtfToRich(rtf)` → `{ text, styles }`: `text` is the plain text (cp1252 `\'xx`, `\u`, ignorable `{\*…}` groups, font table skipped), `styles` is a parallel per-code-unit array of `{bold,italic,underline,color}`. It tracks `\b`/`\i`/`\ul`/`\cf` scoped to RTF `{…}` groups and parses `\colortbl` to resolve `\cf` to hex; `\fs`/`\f` (size/family) are intentionally dropped — EW absolute metrics fight Cue's template sizing. **Inline emphasis is preserved as Cue runs**: after `parseSections`, `deriveStyleJson(content, text, styles)` greedily re-aligns each cleaned section back onto the styled source (sound because the whole pipeline only *deletes* characters, so content is always a subsequence), promotes attributes uniform across the section to section-level style, and emits the rest as `runs` — returning a `style_json` string or `null` (all-default ⇒ null). EW *theme* styling (font/size/background/position) lives outside the RTF and is not imported, so songs that only inherited a theme import default-styled. Auto-resolved colours black/white and `\cf0` (auto) yield no run. Plain `SELECT` only + JS sort — the song table's custom `UTF8_U_CI` collation isn't registered. One `.db` → many rows. EW import runs `parseSections(text, {stripAnnotations:true})`: voice-part / performance directive lines that are not lyrics ("All", "All - Unison", "Men:", "(Women)", "Instrumental", "x2" — `NONLYRIC_TOKENS` / `isNonLyricLine`) are dropped, and a section header trailed by a directive ("Verse 1 - All", "Chorus (Men)") keeps only the section word. `stripAnnotations` is EW-only — plain-text/paste callers leave it off so existing behaviour is unchanged.

`importSongs` (db/songs.js) is tag-aware: each row's `tags[]` (names) is get-or-created (`_IMPORT_TAG_COLOUR` gives GHS a distinct blue) and assigned, and it persists each section's `style_json` (so EasyWorship runs survive — other parsers leave it `undefined` → null). `existingTitleSet()` flags duplicates (default-unselected in the modal).

### GHS hymnal (bundled)
`resources/ghs/ghs-hymnal.json` ships 260 Gospel Hymns & Songs (`scripts/build-ghs.mjs` builds it from a cp1252 number→name CSV + per-number lyric files). On startup `seedGhsHymnal()` imports them once (gated by the `ghs_seeded` setting so deletions stick) and always runs `tagGhsSongs()` — an idempotent backfill that tags every `GHS N …` song with the `GHS` tag. In `LibraryPanel`, the `GHS` tag is the GHS folder; selecting it sorts the list by hymn number and swaps the text search for a numeric quick-search (type a number → that hymn first; Enter previews the exact match).

`patchGhsPunctuation()` (`db/songs.js`, also called from `seedGhsHymnal`) is a one-time content backfill for OCR punctuation artefacts (sustain-dot runs like `". . ."`, mangled words) in five bundled hymns — gated by the `ghs_punct_fix_v1` setting, substring-level `REPLACE()` scoped to `title GLOB 'GHS [0-9]*'` so it's independent of how a song was later re-sectioned, idempotent, and leaves user-edited lines alone (an edited line no longer matches the broken fragment).

`patchGhs7Lyrics()` is a second one-time backfill (gated by `ghs7_lyrics_fix_v1`): GHS 7 "Turn Your Eyes Upon Jesus" shipped with GHS 9's lyrics; the JSON is corrected and existing installs are rewritten only while they still hold the wrong text, so a user's own fix is kept.

### Paste Song List (`songs.matchTitles` + `SongListImportModal.jsx`)
Operators paste set lists that are rarely clean titles: list numbers, leaders and keys (`1. Way Maker - Mary (Key: E)`), segment headers (`PRAISE (fast)`, `WORSHIP:`), first lyric lines instead of titles, and whole pasted lyrics with singer names. All segmentation and matching lives in the pure `src/shared/setlist-match.js` (`matchSetList(raw, lib)`); `db/songs.js matchTitles` only injects the SQLite/FTS library.
- **Segmentation at line grain.** Each line is a unit; boundaries are HARD (a list number, a segment header) or SOFT. Library evidence decides soft boundaries: two units that hit the same song, or a line that continues the previous unit's lyrics, merge; a line with its own confident match splits. A blank-line block is never assumed to be one song (that collapsed a grouped 13-song list to 3).
- **Match tiers**, in order: learned alias (`song_aliases`, v35; beats even an exact title), hymn number (`GHS 7`), exact title (`titleKeys`), first line, then fuzzy title/lyric overlap (`ftsQuery` OR-recall over `songs_fts`, scored by `rankByOverlap`: longest verbatim phrase, lyric coverage, title overlap). `norm`/`ftsQuery`/`rankByOverlap` are shared with the Songs-tab `search()` lyric fallback.
- **Modal:** a live "detected" pane shows the matcher's segmentation with a per-row reason, folded lines expandable, and inline **Create from lyrics** (runs the pasted text through `lyrics-parse` into a prefilled `SongEditor`, rendered as a sibling of the backdrop so clicks don't bubble to its `onCancel`). Each row has a confidence badge, a search-to-replace dropdown and a preview of the matched song. Confirming remembers every operator correction via `songs.rememberAliases` and batch-appends the selected songs to the rundown.
- Tests: `setlist-match.test.mjs` (in `npm test`).

### Arrangements (played section order) — schema v31
`songs.arrangement_json` = JSON array of **0-based section positions** with repeats allowed (e.g. `[0,1,2,1,3,1]` = V1 C V2 C V3 C); NULL = natural order. **Positions, never ids** — `songs.update()` rewrites `song_sections` on every save so ids churn; `db/songs.js serializeArrangement` normalises/clamps and the editor saves arrangement + sections together.

Expansion: `expandSongSections(sections, arrangement)` (`utils/sectionLabels.js`) resolves via `applyArrangement` — labels are computed on the NATURAL list first, so a repeated chorus stays "Chorus" and slide `_key`s carry the arranged position for uniqueness. Every slide-index consumer (operator rail, GO paths, remote `slidesForRemote`, stage next-slide) flows through `OperatorView.getSlides`, so the arrangement applies uniformly. Stale indices are dropped; an all-stale/empty arrangement falls back to natural order (a song never expands to zero slides).

Editor: `ArrangementPanel` (bottom of the sections sidebar) — "+ Create" seeds the natural order; rows are dnd-kit sortable (`i:key` composed ids so repeats sort independently), a select appends sections, Reset returns to natural. In-session it tracks section `_key`s (stable across editor reorders), hydrating ids→keys on load and serializing keys→positions on save; `deleteSection` strips deleted keys.

### Max lines / slide (auto-pagination) — schema v33
A section longer than a line cap auto-splits into multiple display slides — deterministic by **typed line breaks** (`content.split('\n')`), not live output geometry the operator/editor don't have. `splitByMaxLines(content, maxLines)` (`utils/sectionLabels.js`) chunks into groups of at most `maxLines` lines; `maxLinesOf(section)` reads a section's theme-applied `style_json.maxLines` (§8).

Cascade (most-specific wins, all 0-safe = unset): **song's own `songs.max_lines`** (Song Editor, forces every section — set to override "all song items adjust to match") → **section's `style_json.maxLines`** (a theme) → **global `song_max_lines` setting** (Settings → Themes) → 0 = unlimited. `expandSongSections(sections, arrangement, {songMaxLines, globalMaxLines})` runs this AFTER the manual `⁂` break (`splitSectionContent`) — each `⁂` part is then independently capped — so a manual break still wins the boundary and `_partIndex`/`_partCount` span the FINAL combined slide list. `OperatorView` passes `item.song?.max_lines` + the live `song_max_lines` default (read the same way as the bg/scale globals, §9); `SongPreviewModal` mirrors the same cascade so its pagination matches output exactly.

### Song usage log / CCLI reporting — schema v31
`song_usage` (song_id, title, author, copyright, used_at) — one row per song aired. `OperatorView` fires `songs:logUsage` on live-song change; `db/songs.js logUsage` dedupes per song within ~12h (a service window), and **snapshots** title/author/copyright (no FK on song_id) so reports survive edits/deletes. `usageReport(from, to)` groups by snapshot and powers Settings → CCLI (`SongUsageSettings.jsx`): date-range table + client-side CSV export (blob download) + confirm-gated Clear Log.
